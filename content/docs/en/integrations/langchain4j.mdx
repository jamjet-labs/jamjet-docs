## What the integration does

`dev.jamjet:langchain4j-jamjet` adds two things to an existing LangChain4j application:

- **Recorded AI services.** Wrap an `AiServices` proxy, and each method call becomes an execution on the JamJet runtime with an outcome event that holds the result or the error.
- **Chat memory on the runtime.** `JamjetChatMemoryStore` is a `ChatMemoryStore` that keeps each conversation's messages in the runtime's event log, so they outlive the process.

Your interface, tools and model configuration do not change. The call runs in your JVM and the runtime holds the record. The runtime does not re-run or resume a LangChain4j call, so a call that was in flight when your process stopped is not continued after a restart.

By default both refuse to run unrecorded: if the runtime cannot record a call or a memory update, you get a `JamjetGovernanceException` instead of a silent gap.

## Setup

### 1. Add the dependency

`langchain4j-jamjet` brings the JamJet runtime client with it. You bring your own LangChain4j and model provider.

#### Maven

```xml
<dependency>
    <groupId>dev.jamjet</groupId>
    <artifactId>langchain4j-jamjet</artifactId>
    <version>0.2.0</version>
</dependency>
```

#### Gradle (Kotlin DSL)

```kotlin
implementation("dev.jamjet:langchain4j-jamjet:0.2.0")
```

#### Gradle (Groovy DSL)

```groovy
implementation 'dev.jamjet:langchain4j-jamjet:0.2.0'
```

0.2.0 is built and tested against LangChain4j 1.12.2.

### 2. Start the JamJet runtime

```bash
docker run -p 7700:8080 -e JAMJET_DEV_MODE=1 jamjetdev/jamjet:0.5.0
```

Dev mode turns off authentication and this image keeps state in memory. Outside dev mode, pass a token with `.apiToken(...)`.

### 3. Configure the client

`JamjetConfig` holds the runtime settings and builds everything else:

```java
import dev.jamjet.langchain4j.JamjetConfig;

var jamjet = new JamjetConfig()
        .runtimeUrl("http://localhost:7700")
        .apiToken(System.getenv("JAMJET_API_TOKEN")) // null in dev mode
        .memoryNamespace("support-bot");
```

| Method | Default | Description |
|--------|---------|-------------|
| `.runtimeUrl(String)` | `http://localhost:7700` | Address of the JamJet runtime |
| `.apiToken(String)` | none | Bearer token. The token decides the tenant |
| `.memoryNamespace(String)` | none | Namespace for chat memory, normally your application's name. Required for `chatMemoryStore()` |
| `.onRuntimeError(RuntimeErrorMode)` | `FAIL_CLOSED` | `FAIL_OPEN` lets calls run unrecorded and reads fall back to an empty memory |
| `.recordContent(boolean)` | `true` | Record call arguments and results. With `false`, only the method, the argument count, the outcome and, on failure, the exception type are recorded |
| `.connectTimeout(int)` | `10` | Connection timeout in seconds |
| `.readTimeout(int)` | `120` | Read timeout in seconds |

`.tenantId(String)` is deprecated and ignored. `.buildClient()` returns the `JamjetRuntimeClient` the other methods use, the same client type as the [Spring Boot starter](/integrations/spring-boot).

## Record an AI service

Your existing code stays as it is:

```java
import dev.langchain4j.model.chat.ChatModel;
import dev.langchain4j.service.AiServices;

public interface ResearchAssistant {
    String research(String topic);
}

ResearchAssistant assistant = AiServices.builder(ResearchAssistant.class)
        .chatModel(model)
        .build();
```

Wrap it once:

```java
ResearchAssistant recorded = jamjet.wrap(assistant, ResearchAssistant.class);

String result = recorded.research("quantum error correction");
```

`JamjetDurableAgent.wrap(assistant, ResearchAssistant.class, client)` does the same with a client you built yourself, and has overloads that take a `RuntimeErrorMode` and the record-content flag.

### What happens on each call

1. On the first call, the wrapper registers the `langchain4j-durable-agent` workflow (`POST /workflows`). Its one node is a `wait` on the `langchain4j.completed` event.
2. It starts an execution (`POST /executions`) whose input names the interface and the method, and holds the arguments as strings unless content recording is off.
3. It calls your AI service. Tools, memory and the model work as before.
4. It appends a `langchain4j.completed` event with `status` `completed` and the result, or `failed` and the error message.

The table shows what happens when the runtime cannot record, in the default fail-closed mode:

| When | Result |
|------|--------|
| Before your service is called (registration or starting the execution) | `JamjetGovernanceException`. Your service is not called. |
| After your service returned | `JamjetRecordingException`. The call ran, and only its record is missing. |
| After your service threw | Your service's exception, with a `JamjetRecordingException` attached as suppressed. |

With `.onRuntimeError(RuntimeErrorMode.FAIL_OPEN)` each of these logs a warning and the call goes on.

## Chat memory on the runtime

```java
import dev.langchain4j.memory.chat.MessageWindowChatMemory;

var memory = MessageWindowChatMemory.builder()
        .chatMemoryStore(jamjet.chatMemoryStore())
        .id("session-1")
        .maxMessages(20)
        .build();

ResearchAssistant assistant = AiServices.builder(ResearchAssistant.class)
        .chatModel(model)
        .chatMemory(memory)
        .build();
```

`chatMemoryStore()` throws `IllegalStateException` if no namespace is set.

### How it works

Each (namespace, memory id) pair is one execution of the `langchain4j-chat-memory` workflow, started on the first write.

| Operation | What happens |
|-----------|-------------|
| `updateMessages(id, messages)` | Appends a `chat_memory` event holding the full message list. |
| `getMessages(id)` | Reads the execution's events (`GET /executions/{id}/events`) and returns the latest message list. Returns an empty list for an id with no history. |
| `deleteMessages(id)` | Appends a `chat_memory_cleared` event. The event log is append-only, so earlier updates stay on the runtime. |

Things to know:

- **The namespace separates applications. It is not access control.** Anything holding a token for the tenant can read and append events on any execution. Set the namespace to your application's name, so two applications on one tenant do not read each other's memory under the same id (LangChain4j's default id is `"default"`).
- **The first access to an id scans executions.** The runtime has no lookup by input, so the first access to a memory id in a process scans `GET /executions` for it (linear in the tenant's execution count) and caches the result. A miss is cached for 30 seconds, so a new conversation scans once.
- **Keep one writer per memory id.** Two replicas that both start the same new id each create an execution and the history splits. After a restart the newest one wins. Route a conversation to one replica.
- **Fail-closed by default.** A runtime error throws `JamjetGovernanceException` rather than reading as an empty memory or dropping a write. `FAIL_OPEN` restores read-empty, drop-write behaviour.

For memory beyond raw chat history, such as entity extraction and semantic recall, see [Engram](/open-source/engram).

## Read the record

Each wrapped call and each memory id is an ordinary runtime execution. List them with `GET /executions` and read one with `GET /executions/{id}/events`. The outcome is an `external_event_received` event with correlation key `langchain4j.completed`. From Java:

```java
import dev.jamjet.spring.client.model.ExecutionEvent;

var client = jamjet.buildClient();
for (ExecutionEvent event : client.listEvents(executionId)) {
    if (event.isExternalEvent("langchain4j.completed")) {
        System.out.println(event.payload());
    }
}
```

The test module of the Spring Boot starter can load these executions in JUnit 5. See [Testing](/integrations/spring-boot#testing).

## Upgrading from 0.1.0

0.1.0 called `/api/v1/...` routes the runtime never served, so nothing was recorded and memory reads came back empty. 0.2.0 calls the runtime's real routes and fails closed by default. Chat memory is keyed by a namespace now. `langchain4j-jamjet` brings the runtime client itself, so you do not need `jamjet-spring-boot-starter` alongside it.
